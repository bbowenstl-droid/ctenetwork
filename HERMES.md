\## Core Responsibilities



This project serves several purposes:



1\. Maintain the CTE Network fantasy football website.

2\. Retrieve current fantasy football information from Sleeper.

3\. Maintain historical league context.

4\. Create CTE Network articles and league content.

5\. Maintain recurring CTE personalities including Concussion Carl and Anita Headcheck.

6\. Publish approved changes to GitHub Pages.



\## Critical Rule



NEVER publish, git push, commit, delete files, or change production content unless Brendan explicitly asks to publish, push, deploy, commit, or make the change live.



If Brendan says:

\- "write it"

\- "draft it"

\- "show me"

\- "preview it"



DO NOT publish.



If Brendan says:

\- "publish it"

\- "send it to the website"

\- "push it"

\- "make it live"



publication is authorized.



\## Data Philosophy



Never guess league information when it can be retrieved.



For current fantasy information, prefer current Sleeper API data.



For historical CTE information, inspect repository data, existing articles, historical records, owner profiles, standings, and other authoritative project files.



Cross-reference multiple project sources when useful.



Separate:

\- current live data

\- historical facts

\- projections

\- editorial jokes/opinions



Do not present projections as completed results.



\## Writing Style



CTE Network writing should sound like a fantasy football sports media network rather than a generic AI summary.



It may contain:

\- trash talk

\- jokes

\- callbacks

\- owner rivalries

\- ridiculous sports-media framing

\- rage bait

\- fake sportsbook-style lines

\- recurring characters



But factual league data must remain accurate.

\## Article Workflow



When Brendan requests an article:



1\. Determine the current NFL/fantasy week.

2\. Retrieve current Sleeper information.

3\. Inspect relevant CTE repository data.

4\. Inspect recent related CTE articles.

5\. Check historical matchup information when relevant.

6\. Identify major players and fantasy implications.

7\. Review Carl/Anita predictions if applicable.

8\. Build the article using verified information.

9\. Show Brendan the finished draft.

10\. Do not publish until explicitly authorized.



\## Publishing Workflow



When publication is explicitly authorized:



1\. Pull/reconcile latest origin/main.

2\. Confirm the working tree will not overwrite unrelated changes.

3\. Create or update the appropriate article file.

4\. Update required article/news indexes.

5\. Preserve existing website structure.

6\. Review the diff.

7\. Commit with a descriptive message.

8\. Push to origin main.

9\. Verify the push.

10\. Verify the live site if possible.



Never force-push main.



Never discard Brendan's uncommitted work merely to make a pull succeed.



\## Safety

\- passwords

\- API keys

\- personal access tokens

\- .env secrets



\## Preferred Behavior



Be direct.



Do research instead of guessing.



If the available data contradicts Brendan's assumption, point out the discrepancy.



When asked for a briefing, prioritize useful information over lengthy explanation.



When asked to perform work, perform it rather than only explaining how it could be done.
